# CP-AI-04 — Catalog Contract

## Source of truth

The maintained catalog is Flutter's `curatedExerciseLibrary` in
`frontend/lib/presentation/providers/exercise_providers.dart`. The
`exerciseLibraryListProvider` returns that list directly. The exporter imports
the provider and serializes its runtime `Exercise` values; it does not parse
Dart text or keep a manually copied exercise list.

## Generated artifact

Path: `backend/app/data/ai_exercise_catalog.generated.json`

The UTF-8 JSON envelope is:

```json
{
  "schema_version": 1,
  "generated": true,
  "generator": "frontend/tool/export_ai_exercise_catalog.dart",
  "source": "frontend/lib/presentation/providers/exercise_providers.dart:curatedExerciseLibrary",
  "source_sha256": "<sha256 of compact serialized exercise records>",
  "exercises": []
}
```

Each exercise preserves the `Exercise.toJson()` fields and order:
`id`, `slug`, `name`, `nameVi`, `muscleGroup`, `targetMuscles`,
`secondaryMuscles`, `equipment`, `difficulty`, `thumbnailUrl`,
`youtubeVideoId`, `cues`, `commonMistakes`, `defaultSets`, `defaultReps`,
`restSeconds`, `repType`, `cvSupported`, and `cvModuleId`. Null optional
values and actual list/string/numeric types are preserved. Records remain in
Library order.

The artifact is generated output. Do not edit it manually. From `frontend`:

```powershell
dart run tool\export_ai_exercise_catalog.dart
dart run tool\export_ai_exercise_catalog.dart --check
flutter test test\ai_exercise_catalog_export_test.dart
```

The first command writes only the artifact after validating all records. The
second compares newly generated bytes and exits nonzero for missing or stale
output without writing. Duplicate IDs, duplicate normalized slugs, blank
required fields, unsupported serialized fields, and `plan_ex_*` canonical IDs
fail closed before output is written. No `pub get` is required.

At CP-AI-04 verification, the runtime Library had 49 entries, 49 unique IDs,
and 49 unique normalized slugs. The count is evidence, not a generator
constant; tests compare the artifact against the current provider list.
The backend validates that the digest matches the serialized records before
building its resolver indexes.

## Backend loading and packaging

`backend/app/services/exercise_catalog_resolver.py` loads the JSON relative
to its own source path, independent of process cwd. It uses only Python
standard-library modules and does not query Mongo or import Flutter/provider
code. Chat imports this leaf resolver without running the existing
`backend.app.services` package initializer. It is wired to both CP-AI-03's
latest-workout history normalizer and the explicit-date history formatter via
`resolve_exercise_name`.

The expected package-relative artifact is
`backend/app/data/ai_exercise_catalog.generated.json`. Deployment packaging
was not inspected or changed, so inclusion in a deployed bundle remains
unverified.

If the artifact is missing, malformed, has duplicate JSON keys/IDs/slugs, or
contains a reserved synthetic canonical ID, the resolver marks the catalog
unavailable. In the CP-AI-03 latest-workout normalizer, the history record
and valid logged metrics remain available as unresolved context; the
explicit-date formatter likewise preserves the logged record and metrics
while displaying an unresolved identity. Neither path falls back to Mongo
for exercise metadata or converts catalog errors into empty history.

## Identity resolution policy

Slug normalization is exactly `strip + lowercase`; IDs are exact and
case-sensitive. No display-name lookup, approximate match, or fuzzy matching
is permitted.

| Stored history identity | Result |
|---|---|
| Known canonical ID only | Resolve by exact ID. |
| No ID and exact known slug | Resolve by exact slug. |
| Known canonical ID and matching normalized slug | Resolve; retain both-field provenance. |
| Known canonical ID and absent/different/unknown supplied slug | Conflict/unresolved; do not attach metadata. |
| Unknown non-synthetic ID, even with a known slug | Unresolved; an unknown ID is not promoted by slug. |
| `plan_ex_*` ID and exact known slug | Resolve by the exact slug only; preserve `synthetic_id` and `exact_slug` provenance, and report the matched catalog ID separately. |
| `plan_ex_*` without an exact known slug | Unresolved; the synthetic ID is never canonical. |
| Missing/invalid artifact | Unavailable; preserve history and metrics without catalog metadata. |

Resolved history receives a defensive copy of catalog metadata, canonical ID,
history-field provenance, and identity-resolution provenance. It does not
rewrite source records or replace logged reps, weight, duration, completion,
or volume with default catalog prescription values.

## Compatibility boundary

The Flutter Library remains local/offline. Exercise models, assets, CV data,
Mongo collections/seeds, backend routes, public Chat response schemas, and
dependencies are unchanged. This contract does not establish deployed Mongo
parity or authorize recommendation behavior.
